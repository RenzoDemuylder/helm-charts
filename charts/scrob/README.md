# Scrob Helm chart

[Scrob](https://github.com/ellite/scrob) is a self-hosted media tracker (a private Letterboxd + Trakt) that syncs watch history from Jellyfin, Plex and Emby.

## TL;DR

```console
helm install my-scrob oci://ghcr.io/renzodemuylder/charts/scrob
```

## Introduction

This chart deploys Scrob on a Kubernetes cluster using the Helm package manager. Scrob requires PostgreSQL: by default the chart deploys a single-instance PostgreSQL StatefulSet (official `postgres` image); use `cnpg.enabled` to create a CloudNativePG `Cluster` instead, or `externalDatabase.*` to point at your own server (including an existing CloudNativePG cluster).

The upstream image starts as root and drops privileges in its entrypoint. This chart overrides the command (run migrations, then start supervisord) so Scrob runs as non-root UID 1000 with a read-only root filesystem and all capabilities dropped.

Values follow the layout and naming conventions popularised by Bitnami charts; shared helpers come from the [`common`](../common) library chart in this repository.

## Prerequisites

- Kubernetes 1.25+
- Helm 3.8+ (4.x supported)
- PV provisioner support in the cluster (for persistence)

## Installing the chart

```console
helm install my-scrob oci://ghcr.io/renzodemuylder/charts/scrob \
  --set ingress.enabled=true \
  --set ingress.hostname=scrob.example.com \
  --set ingress.tls=true
```

Open the URL and create the first user. TMDB, TVDB and MDBList API keys are set in the web UI.

## Configuration and installation details

### Secrets

`secretKey` (session signing key) and the PostgreSQL password are generated on first install and reused on upgrades (via `lookup`). To manage secrets yourself, create a Secret and set `existingSecret` (keys: `secret-key`, and as needed `oidc-client-secret`, `trakt-client-secret`, `smtp-password`, `database-password`).

### External database

```yaml
postgresql:
  enabled: false
externalDatabase:
  host: postgres.example.com
  user: scrob
  database: scrob
  existingSecret: scrob-db        # Secret with the password
  existingSecretKeys:
    password: password
```

### CloudNativePG cluster created by the chart

With the [CloudNativePG](https://cloudnative-pg.io) operator installed in the cluster, the chart can create the `Cluster` for you:

```yaml
postgresql:
  enabled: false
cnpg:
  enabled: true
  instances: 3
  storage:
    size: 20Gi
  annotations:
    helm.sh/resource-policy: keep   # keep the cluster and its data on `helm uninstall`
  extraSpec:                        # any other Cluster spec: backups, monitoring, parameters...
    postgresql:
      parameters:
        max_connections: "200"
```

Scrob connects to the `<release>-scrob-db-rw` service with the credentials in the `<release>-scrob-db-app` Secret that the operator generates. `postgresql.enabled` and `cnpg.enabled` are mutually exclusive. Without `helm.sh/resource-policy: keep`, uninstalling the release deletes the cluster and its volumes.

### Existing CloudNativePG cluster

Create a `Cluster` (or reuse one) with a database and owner for Scrob, then point the chart at the Secret CloudNativePG generates (`<cluster>-app`, keys `host`, `port`, `username`, `password`, `dbname`). Nothing else is needed: host, port, user and database are all read from the Secret.

```yaml
postgresql:
  enabled: false
externalDatabase:
  existingSecret: scrob-db-app    # <cluster>-app
  existingSecretKeys:
    host: host
    port: port
    user: username
    password: password
    database: dbname
```

The Secret must be in the same namespace as the release. With `networkPolicy.allowExternalEgress=false`, add an egress rule for the database pods through `networkPolicy.extraEgress`.

### OIDC

```yaml
serverUrl: https://scrob.example.com
oidc:
  enabled: true
  providerName: Authentik
  clientId: scrob
  clientSecret: change-me
  discoveryUrl: https://auth.example.com/application/o/scrob/.well-known/openid-configuration
```

### Single replica

Scrob keeps avatars and image cache on a local volume, runs in-process schedulers and migrates the database on start. `replicaCount` above 1 is rejected, and the Deployment uses the `Recreate` strategy.
